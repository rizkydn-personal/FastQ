# FastQ POS

Aplikasi kasir web offline-first untuk toko ritel dan F&B skala kecil. Cakupan fitur mengikuti modul MVP dan sebagian fitur rilis 2 di PRD; cek batas implementasi sebelum pilot.

## Deploy web ke Render

Repository menyertakan `render.yaml` untuk membuat satu layanan Node.js di Render. Blueprint menjalankan `npm ci && npm run build`, lalu `npm start`; Render mengatur port layanan secara otomatis. Hubungkan repository Git ke Render dan pilih **New > Blueprint** untuk membaca konfigurasi tersebut.

Sebelum deploy pertama, siapkan PostgreSQL terkelola yang akan dipakai sebagai database bersama. Gunakan koneksi runtime berhak terbatas pada `DATABASE_URL` dan jalankan migrasi skema satu kali dari komputer admin dengan `POS_MIGRATION_DATABASE_URL` serta `PGSSLMODE=verify-full` sesuai konfigurasi penyedia database. Di PowerShell, isi variabel tersebut untuk sesi terminal lalu jalankan `npm run db:migrate`. Jangan gunakan database gratis Render untuk data toko jangka panjang: [database gratis Render kedaluwarsa setelah 30 hari](https://render.com/docs/free). Periksa batas paket gratis penyedia database sebelum menyimpan transaksi produksi.

Saat membuat Blueprint, isi `DATABASE_URL` ketika diminta. Render membuat `POS_SESSION_SECRET` dan `POS_API_TOKEN`; jangan mengganti secret sesi setelah kasir mulai login karena sesi yang sudah ada menjadi tidak berlaku. Jika TOTP dipakai, tambahkan `POS_TOTP_ENCRYPTION_KEY` berisi 64 karakter hex dan simpan salinannya di pengelola secret yang aman; kunci yang berbeda tidak dapat membuka secret TOTP yang sudah terenkripsi.

`.env` lokal, backup, database lokal, `node_modules`, build `dist`, dan folder `public` hasil generate tidak masuk ke Git. Jangan menambahkan kredensial atau data toko ke repository. `public/` dibuat ulang oleh `npm run build` dari berkas sumber project.

## Menjalankan lokal

Gunakan Node.js 20 atau lebih baru:

```sh
npm install
npm test
npm run db:migrate
npm run dev:all
```

Buka `http://localhost:5173`. Perintah tersebut menjalankan API pada port 4173 dan Vite pada port 5173. Jika API sudah berjalan terpisah, cukup jalankan `npm run dev`. Untuk menyajikan build produksi, jalankan `npm run build && npm start`, lalu buka `http://localhost:4173`. Akses localhost/HTTPS diperlukan untuk PWA, Web Crypto, authenticator, dan WebUSB. Shell PWA baru tersedia offline setelah halaman pertama kali dimuat. Data kasir disimpan pada perangkat/browser yang sama.

`npm run db:smoke` menjalankan event shift, audit, absensi, kas, penjualan/retry, pembayaran piutang, permintaan/pembatalan diskon, pengurangan stok, dan pull event sinkronisasi melalui handler aplikasi dengan koneksi `DATABASE_URL`, lalu mengganti commit menjadi rollback dan memastikan row uji hilang serta saldo stok awal tetap sama, dan memeriksa bahwa persetujuan, pembayaran piutang, penjualan, serta pengurangan stok benar-benar diterapkan sebelum rollback; smoke test juga mengirim ulang transaksi dengan ID event baru dan timestamp yang sama untuk memeriksa idempotensi. Gunakan setelah migrasi atau perubahan handler database; perintah ini memerlukan database siap serta satu akun Kasir aktif dan Pemilik aktif pada outlet yang sama; smoke test juga melewati persetujuan kas/diskon oleh Pemilik.

Pada instalasi baru, buka `/pos`, pilih **Daftar dan buat toko**, lalu isi nama toko, nama Pemilik, email atau nomor HP, dan password minimal 10 karakter. Login kasir maupun dashboard menggunakan email/nomor HP + password, tanpa OTP email/SMS; akun lama dengan authenticator tetap memerlukan kode authenticator. Nomor HP Indonesia `08...`, `628...`, dan `+628...` dinormalisasi menjadi identitas yang sama. Email/nomor HP harus unik lintas akun.

POS lokal hanya menampilkan dan mempertahankan outlet yang dikonfirmasi server saat login. Outlet dummy bawaan dan outlet yang dibuat hanya di perangkat tidak dapat dipakai untuk transaksi/sinkronisasi; pembuatan outlet server belum tersedia sebagai fitur multi-outlet akun.

Server otomatis membuat ID toko publik unik enam angka (`100000`–`999999`) dengan sequence database tanpa pengulangan; UUID internal tetap dipakai untuk relasi transaksi. ID toko tidak perlu diketik saat login. Outlet lama mendapat kode saat migrasi schema. PostgreSQL dan `POS_SESSION_SECRET` minimal 32 karakter wajib tersedia. Setelah login online berhasil, sesi kasir berlaku hingga 30 hari dan dapat dipakai offline; logout atau sesi kedaluwarsa membutuhkan login online kembali. Akun lama tanpa email/nomor HP belum dapat login melalui alur baru: administrator perlu mengisi `users.login_identity` dengan identitas ternormalisasi yang benar, tanpa mengubah UUID atau hash password. Kasir lama yang belum punya password juga memerlukan pengaturan password oleh administrator. Jangan membuat toko pengganti untuk memigrasikan data toko lama.

Pemilik dapat membuat akun dan toko melalui pendaftaran; Admin dapat menonaktifkan akun, tetapi tidak dapat membuat akun atau toko. Manajer hanya dapat melihat dan mengekspor data. Admin memiliki kontrol operasional penuh, sedangkan Kasir hanya dapat bertransaksi, mengelola shift, dan absen; Kasir tidak dapat mengubah data atau memproses refund. Kas keluar Kasir berstatus menunggu dan tidak dihitung pada kas shift sampai disetujui atau ditolak oleh Admin/Pemilik; kas keluar yang dibuat Admin/Pemilik langsung disetujui. Perubahan akun memerlukan koneksi server, dan akun aktif sendiri tidak dapat dihapus. Gunakan profil browser terpisah untuk outlet berbeda agar snapshot lokal tidak bercampur. Buat katalog produk sendiri; aplikasi tidak mengisi transaksi atau barang contoh.

## Fitur yang tersedia

- POS: pencarian nama/SKU, grid favorit yang dapat dikonfigurasi, scanner barcode keyboard, scanner native Android, dan kamera browser yang mendukung Barcode Detection API; kategori, keranjang, catatan dan diskon item/transaksi, hold, pajak inklusif/eksklusif, service charge, tunai/kartu/transfer/QRIS, split payment, piutang berbasis nomor transaksi, kembalian, struk. Scanner native memasang modul Google saat pertama kali diperlukan; koneksi internet mungkin dibutuhkan untuk pemasangan awal.
- Produk: CRUD dengan ikon produk opsional yang otomatis dikompresi, varian, harga/modal, satuan, pergerakan stok beralasan, minimum stok, CSV UTF-8 impor/ekspor.
- Operasional: shift, absensi masuk/pulang, kas masuk/keluar dengan persetujuan kas keluar Kasir, tutup dan rekonsiliasi kas, outlet, transfer stok, piutang berbasis nomor transaksi tanpa profil pelanggan, kas kecil berkategori, void tertunda/gagal dengan alasan dan persetujuan PIN Admin, serta refund transaksi lunas/piutang dengan alasan, metode, referensi, persetujuan Admin, pembatalan sisa piutang, opsi pengembalian stok, dan catatan kas keluar untuk refund tunai.
- Laporan: periode harian/mingguan/bulanan, produk/kategori/kasir/metode bayar, laba kotor, tren dan stok menipis, CSV dan dialog cetak/PDF.
- Pengguna: empat role (Pemilik, Manajer, Admin, Kasir) dengan izin yang diterapkan pada UI dan endpoint server; sesi berlaku hingga 30 hari; password pengelola dan TOTP opsional. Persetujuan tindakan istimewa memakai PIN Admin. Snapshot kerja lokal dienkripsi AES-GCM di IndexedDB; data `localStorage` lama dienkripsi saat migrasi pertama.
- Untuk mengukur biaya snapshot pada perangkat berisi data nyata, buka konsol developer pada konteks halaman POS dan jalankan `window.PosLocalStorage.getWriteDiagnostics()`. Hasil hanya berada di memori dan berisi jumlah tulis, ukuran snapshot dalam karakter, durasi serialisasi/enkripsi/tulis, jenis penyimpanan, serta status retry; data transaksi tidak ikut dicetak.
- Dashboard web `/owner`: login Pemilik/Manajer/Admin dengan password dan TOTP jika diaktifkan; sesi berlaku hingga 30 hari; ringkasan omzet, tren, transaksi, kategori, metode pembayaran, kasir, piutang, serta stok menipis per outlet/periode.
- Struk: template logo/nama/alamat/catatan, cetak browser/PDF, tautan berbagi WhatsApp, serta ESC/POS lewat USB native Android, USB/WebUSB browser, Bluetooth LE/Web Bluetooth, Bluetooth Classic SPP native Android untuk printer yang sudah dipasangkan, printer LAN raw TCP yang dikonfigurasi di server, atau dialog cetak browser.
- Sinkronisasi: antrean event delta stok dan sinkronisasi otomatis setelah login, perubahan data, atau koneksi pulih; konflik stok memakai alur hitung fisik dan persetujuan PIN supervisor. Backup PostgreSQL dikelola di server melalui Compose; tidak ada opsi backup atau sinkronisasi manual di UI POS.

## Server PostgreSQL dan sinkronisasi otomatis

Sinkronisasi event POS memakai sesi login aktif. Server memvalidasi akun aktif, membatasi data ke outlet akun, dan menolak event yang tidak sesuai role; Manajer hanya membaca, Kasir hanya menyinkronkan transaksi/shift/absensi, dan perubahan produk hanya dapat dikirim Admin. Klien hanya mengirim antrean yang diizinkan untuk role dan outlet aktif; event lain tetap lokal, tidak dihapus atau dipindahkan kepemilikannya. Sinkron berjalan otomatis setelah login, perubahan data, dan koneksi pulih. Tidak ada kontrol sinkronisasi manual di POS. Backup server dikelola oleh layanan PostgreSQL; token API server tetap digunakan untuk layanan server seperti printer LAN. Konflik stok menghentikan batch dan mempertahankan antrean lokal untuk pemeriksaan, bukan membuang perubahan.

1. Salin `.env.example` menjadi `.env`. Ganti `POSTGRES_PASSWORD`, `POS_ADMIN_PASSWORD`, `POS_APP_PASSWORD`, dan `POS_BACKUP_PASSWORD` dengan password acak yang berbeda; samakan password URL `POS_MIGRATION_DATABASE_URL` dengan `POS_ADMIN_PASSWORD` dan URL `DATABASE_URL` dengan `POS_APP_PASSWORD`. Gunakan nilai acak berbeda minimal 32 byte untuk `POS_API_TOKEN` dan `POS_SESSION_SECRET`. Isi `POS_TOTP_ENCRYPTION_KEY` dengan 32 byte acak dalam 64 karakter heksadesimal jika TOTP diaktifkan untuk akun pengelola. Pasang Docker serta Docker Compose.
2. Jalankan `docker compose up -d`. Ini menyalakan PostgreSQL 18 dengan arsip WAL terkompresi untuk PITR, dump harian 30 hari, dan base backup PITR harian 7 hari. Base backup diverifikasi dengan `pg_verifybackup`; bila gagal, layanan mencoba lagi setelah lima menit. WAL dikirim paling lambat sekitar lima menit setelah segmen terbentuk dan disimpan 10 hari. Healthcheck layanan dump dan base backup berstatus `unhealthy` bila marker sukses belum ada atau lebih lama dari 26 jam, setelah masa awal 10 menit; pantau `docker compose ps` atau hubungkan status health ke monitor berbiaya rendah. Semua file berada di volume lokal Docker.
3. Jalankan `npm install`, lalu `npm run db:migrate` sebelum `npm start`. Migrasi memakai `db/schema.sql` untuk baseline dan file bernomor di `db/migrations/` untuk perubahan berikutnya; server aplikasi tidak menjalankan DDL saat startup. Migrasi wajib memakai `POS_MIGRATION_DATABASE_URL` untuk role `pos_admin`; script menolak berjalan bila variabel ini belum diatur dan tidak pernah fallback ke `DATABASE_URL`. `DATABASE_URL` hanya untuk role runtime `pos_app` yang tidak memiliki hak DDL dan hanya dapat membaca tabel `schema_migrations`. `POSTGRES_PASSWORD` hanya untuk bootstrap superuser PostgreSQL dan harus berbeda dari `POS_ADMIN_PASSWORD`. Password role aplikasi, migrasi, dan superuser juga harus berbeda satu sama lain; script bootstrap menolak password yang sama. Setelah migrasi, jalankan `npm run db:status` untuk pemeriksaan read-only role runtime dan versi skema; perintah ini tidak mencetak URL atau secret. Pada instalasi baru, Compose menyiapkan role aplikasi, migrasi, dan backup dengan hak terpisah. Server menahan API bila role `DATABASE_URL` atau role yang dapat diaktifkannya memiliki superuser, CREATE, BYPASSRLS, atau kepemilikan database/objek public. `npm start` menyajikan build web di port 4173 dan menolak permintaan file statis jika build belum dibuat. Jika hak role runtime, database, atau skema belum siap, server tetap melayani `/api/health/live`, readiness mengembalikan 503, dan endpoint API ditahan dengan 503. Tiap request API/readiness memakai hasil pemeriksaan paling lama lima detik; pemeriksaan berikutnya mengunci API bila hak role, koneksi, atau skema tidak lagi siap. Saat pengembangan, jalankan `npm run dev` di terminal lain; Vite menggunakan server API di port 4173. Sesi disimpan sebagai cookie HttpOnly; `POS_TOTP_ENCRYPTION_KEY` mengenkripsi secret authenticator di database dan harus dicadangkan aman.
4. Jadwalkan `npm run db:maintenance` sekali sehari. Tugas ini menghapus backup aplikasi yang lebih lama dari 90 hari. Event sinkronisasi belum dihapus otomatis karena bootstrap snapshot untuk perangkat baru belum tersedia; menghapus event tanpa bootstrap berisiko membuat perangkat baru menerima data tidak lengkap. Untuk printer LAN, isi `POS_PRINTER_HOST` dan `POS_PRINTER_PORT` di `.env` pada server yang satu jaringan dengan printer, dan atur `POS_API_TOKEN` khusus layanan printer. Jika memakai reverse proxy, set `POS_TRUST_PROXY=true` hanya bila proxy tepercaya menimpa header alamat, host, dan protokol (`X-Real-IP`, `X-Forwarded-For`, `X-Forwarded-Host`, `X-Forwarded-Proto`). Cookie sesi memakai flag Secure secara default; pada pengembangan HTTP lokal saja, set `POS_COOKIE_SECURE=false` bila browser tidak menerima cookie localhost. Login POS memakai cookie sesi; akun dashboard mengikuti role pengguna.

Untuk database terkelola, set `PGSSLMODE=verify-full`. `require` juga mengaktifkan verifikasi sertifikat pada aplikasi ini. Bila CA provider tidak ada dalam trust store sistem, isi `PGSSLROOTCERT` dengan path file root CA PEM yang diunduh dari dashboard provider; path relatif dihitung dari direktori project. Nilai kosong hanya sesuai untuk PostgreSQL Docker lokal. `npm run db:status` menampilkan status TLS socket (`verified`, `unverified`, atau `disabled`). Jangan menonaktifkan verifikasi sertifikat untuk mengatasi error TLS. Lihat [panduan SSL PostgreSQL Supabase](https://supabase.com/docs/guides/platform/ssl-enforcement).

Untuk instalasi baru, init script membuat role runtime `pos_app` tanpa hak DDL serta role `pos_backup` dengan hak baca dan replikasi terbatas. Role migrasi `pos_admin` memiliki database dan objek aplikasi tetapi bukan superuser. Pada volume PostgreSQL lama yang sebelumnya memakai `pos_app` sebagai superuser, isi `POS_APP_PASSWORD`, `POS_ADMIN_PASSWORD`, dan `POS_MIGRATION_DATABASE_URL` dengan password admin yang sama, lalu jalankan sekali `docker compose exec -e POS_BOOTSTRAP_USER=pos_app postgres sh /docker-entrypoint-initdb.d/002-app-role.sh`. Script membuat `pos_admin`, memindahkan kepemilikan objek ke role admin, lalu menurunkan hak `pos_app` dan `pos_admin`; setelah itu isi `DATABASE_URL` dengan password aplikasi dan `POS_MIGRATION_DATABASE_URL` dengan password admin. Jalankan migrasi sebelum server kembali digunakan. Pada database lama, buat role backup satu kali sebagai admin sebelum menjalankan layanan backup: `docker compose exec postgres sh /docker-entrypoint-initdb.d/003-backup-role.sh`. Jika role backup sudah ada, ubah password dan berikan privilege yang sama, jangan jalankan `CREATE ROLE` lagi.

Target pemulihan awal untuk kegagalan host yang volume lokalnya masih utuh: **RPO ≤ 5 menit** dan **RTO ≤ 4 jam**, dihitung sejak backup PITR pertama selesai dan alur restore staging sudah diuji. Untuk kegagalan host/perangkat penyimpanan, target ini belum berlaku sampai salinan terenkripsi offsite dijadwalkan dan diuji; volume Docker di host yang sama bukan salinan offsite.

Periksa checksum dan struktur dump terbaru dengan `docker compose exec backup sh -c 'cd /backups && file=$(ls -1t pos-*.dump | head -n 1) && sha256sum --check "$file.sha256" && pg_restore --list "$file" >/dev/null'`. Periksa base backup terbaru dengan `docker compose exec pitr-backup sh -c 'file=$(find /backups/pitr -maxdepth 1 -type d -name "base-*" | sort | tail -n 1); test -n "$file" && pg_verifybackup "$file"'`. Untuk uji PITR staging, pilih nama backup lewat `docker compose exec pitr-backup ls -1 /backups/pitr`, lalu siapkan volume staging kosong dengan `docker compose run --rm -e BASE_BACKUP=base-YYYYMMDDTHHMMSSZ -e "RECOVERY_TARGET_TIME=2026-11-14 04:30:00+00" --entrypoint /bin/sh pitr-backup /prepare-pitr-restore.sh`. Ganti nama backup dan waktu target UTC sesuai kebutuhan. Setelah script menyatakan siap, jalankan `docker compose --profile restore up -d postgres-restore`; service ini hanya membuka port `127.0.0.1:5433` dan volume `pos-restore`, terpisah dari database aktif. Periksa log dan data hasil recovery sebelum cutover. Script menolak volume staging yang tidak kosong. Jangan arahkan pemulihan ke volume database aktif.

### Backup terenkripsi offsite ke S3-compatible storage

Layanan offsite bersifat opsional dan memakai image resmi Restic yang dipatok ke versi `0.19.1`. Isi `.env` dengan URL repository S3, access key khusus bucket backup, region, serta kata sandi Restic acak yang kuat dan berbeda dari kredensial S3. Repository Restic mengenkripsi data di sisi klien; simpan kata sandi Restic di pengelola secret terpisah karena tanpa kata sandi tersebut snapshot tidak dapat dipulihkan.

Inisialisasi repository satu kali, lalu aktifkan jadwal backup harian:

```sh
docker compose --profile offsite run --rm offsite-backup init
docker compose --profile offsite up -d offsite-backup
docker compose logs -f offsite-backup
```

Layanan membaca dump harian, base backup PITR, dan arsip WAL dari volume lokal dengan mount read-only. Ia membuat snapshot langsung, mencoba lagi tiap lima menit saat gagal, memeriksa repository, menyimpan 30 harian/12 mingguan/12 bulanan, dan memangkas data repository setiap hari Minggu. Healthcheck offsite berstatus `unhealthy` bila marker sukses belum ada atau lebih lama dari 26 jam, setelah masa awal 30 menit; hubungkan status tersebut ke monitor uptime/alert. Untuk pemulihan file ke volume staging terpisah yang masih kosong, jalankan `docker compose --profile offsite run --rm offsite-backup restore latest --target /restore`. Layanan menolak target restore yang tidak kosong. Setelah snapshot selesai dipulihkan, impor ke volume backup lokal yang kosong dan verifikasi base backup dengan:

```sh
docker compose --profile offsite-restore run --rm offsite-restore-import
```

Importer menolak volume tujuan yang berisi data dan menjalankan `pg_verifybackup`; jika dump SQL tersedia, ia juga memeriksa checksum dan strukturnya. Setelah itu ikuti langkah PITR staging di atas. Uji pemulihan penuh sebelum pilot dan simpan kata sandi Restic di luar host aplikasi.

Untuk perangkat tablet, server harus dipublikasikan melalui reverse proxy HTTPS. Server bawaan hanya listen di `127.0.0.1` dan cocok untuk pengembangan lokal. Halaman root menampilkan landing FastQ bagi pengunjung, dashboard tersedia di `/owner`, dan POS di `/pos`. Dashboard, sinkronisasi perangkat, dan backup aplikasi memakai sesi bertanda tangan 30 hari serta pembatasan role; token API bersama hanya dipakai layanan printer LAN dan perlu dibatasi di jaringan server.

## Impor CSV/Excel

Kolom wajib: `nama`, `sku`, `harga_jual`. Kolom opsional: `barcode`, `kategori`, `harga_modal`, `satuan`, `stok`, `stok_minimum`, `variants`. `variants` menggunakan JSON hasil ekspor. ## Batas sebelum penggunaan produksi

- POS saat ini dijalankan di dalam shell React/TypeScript + Capacitor dan layar transaksi masih berupa halaman legacy dalam iframe. Pada browser, snapshot lokal dienkripsi AES-GCM di IndexedDB. Pada Android/iOS, snapshot POS disimpan di SQLite/SQLCipher terenkripsi dengan secret perangkat. Jalur native, migrasi data legacy ke SQLite, dan build APK masih perlu diverifikasi pada emulator/perangkat.
- Web Bluetooth hanya untuk printer BLE dengan karakteristik GATT write yang kompatibel; Android juga dapat mengirim ESC/POS melalui Bluetooth Classic SPP ke perangkat yang sudah dipasangkan. Kompatibilitas tetap bergantung pada printer. Printer LAN memakai satu alamat tetap di konfigurasi server; belum ada pemilihan printer per outlet. Android shell dapat disiapkan dengan `npm run android:add`, lalu `npm run cap:sync`; build APK memerlukan Android SDK. Integrasi WhatsApp API dan integrasi akuntansi/e-commerce belum tersedia. Tautan WhatsApp membuka aplikasi pesan; WebUSB/Web Bluetooth memerlukan browser dan izin yang mendukung.
- Sinkronisasi dan backup aplikasi memerlukan PostgreSQL serta konfigurasi HTTPS/token. Snapshot terenkripsi aplikasi hanya diunggah saat aplikasi berjalan; dump, base backup, dan WAL PITR lokal dapat dicadangkan terenkripsi ke S3-compatible storage dengan profil `offsite`, tetapi kredensial serta kata sandi Restic perlu diisi oleh operator. Backup lokal berjalan terlepas dari layanan offsite. Restore staging tersedia lewat profil Compose, tetapi alur database belum dijalankan pada mesin ini; uji restore sebelum pilot tetap wajib. Endpoint `/api/health/live` memeriksa proses dan `/api/health` memeriksa readiness database serta status TLS socket (`databaseTls`); hubungkan endpoint readiness ke monitor uptime eksternal dan alert operator. Pengukuran target uptime 99,5% tetap perlu berjalan pada lingkungan produksi. Konflik stok perlu hitung fisik dan persetujuan supervisor.
- Akun Pemilik/Manajer/Admin dapat mengakses dashboard sesuai role; sesi dashboard memakai password serta kode TOTP bila akun mengaktifkannya, dengan masa berlaku 30 hari. Sinkronisasi data dan backup aplikasi memakai sesi role-aware; token API bersama hanya dipakai printer LAN. Integrasi WhatsApp Business API belum tersedia. Bluetooth Classic SPP dan USB Host memiliki bridge native; pasangkan Bluetooth melalui Pengaturan Android dan sambungkan printer USB dengan kabel OTG. Pemulihan PITR dan backup offsite sudah memiliki alur Compose, tetapi belum diuji terhadap PostgreSQL/S3 sungguhan; uji perangkat/printer dan uji lapangan juga belum dilakukan. Scanner ML Kit dan cetak Bluetooth Classic/USB native perlu diverifikasi pada perangkat serta printer target. Karena itu metrik transaksi 15 detik, operasi offline 24 jam tanpa kehilangan data, crash-free 99,5%, dan kriteria penerimaan MVP belum boleh dianggap tervalidasi.
